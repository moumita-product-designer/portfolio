CASE STUDY · CURIE DESIGN SYSTEM

One source of truth for Curie: building a design system that people, code and AI design tools all build from

How I turned Curie's visual language — scattered across Figma files and hand-built pages — into a versioned design system with tokens, 68 desktop and 61 mobile components, responsive page templates, charts, an asset library and a generated documentation site, and how the team now uses it inside Claude Design to produce on-brand mockups every week.

Product

Curie (curie.md), ZoomRx's dark-themed medical-content platform for healthcare professionals: Briefs, Podcasts, Editorial, Games and the Weekly Dose newsletter

What I built

The Curie Design System: the package/ source of truth (tokens, CSS, component manifests, golden page templates, brand principles, assets) and the documentation site generated from it

My role

Product designer — sole designer and builder of the system, from audit to adoption

1. The problem statement

Curie is a small team shipping quickly. In 2026 the product was growing on every surface at once — Briefs, Podcasts, Editorial, Games, the newsletter, and the Play & Learn area — with new features going out almost every week. Curie already had a strong and recognisable look: a dark purple canvas, frosted-glass cards, Manrope with a touch of Playfair Display, purple as the brand colour and teal as a sparing accent. The trouble was that this look only existed implicitly.

1.1 Where the visual language lived

  • In Figma files, as screens and a components page — readable by designers, but not by code or by AI tools.
  • In hand-built HTML pages, where values were typed in directly: a purple here, a 9.6px spacing there.
  • In people's heads, as rules nobody had written down: "Playfair only for a hero headline", "one accent per view", "never a white card".

1.2 What that cost the team

SymptomWhat it meant in practice
Every mockup started from scratchThere was no shared kit to design on top of. Each new feature screen meant rebuilding cards, headers and buttons, and re-deciding spacing and colour.
Brand driftValues were copied by eye, so they drifted. Later, during the codebase hand-off, I measured three different values for "primary purple" in use at the same time: #6153be (the brand), #6153bd (an internal guide) and #8b5cf6 (what the app actually rendered).
AI design tools produced generic outputThe team was starting to use Claude Design for mockups. Without Curie's tokens, components and rules to work from, it produced its own interpretation — competent, but not Curie.
Unclear handoffsDevelopers received screens, not specifications. Hover, focus, disabled and loading states, motion, and mobile behaviour were left to guesswork.
No mobile specificationCurie was designed desktop-first. There was no agreed answer for how each page should behave on a phone.
Gaps found lateCommon patterns — a systematic button, form states, modals, tabs, charts, everyday UI icons — did not exist as reusable pieces, so each feature invented its own.
The problem in one sentence

Curie had a distinctive design language but no single, machine-readable source of truth for it — so every designer, developer and AI tool had to re-interpret it, and every re-interpretation was a chance for the product to drift off-brand and for work to slow down.

2. Goals and principles

I set out to build a system that would serve three kinds of reader equally: designers who need to see and copy, developers who need exact specifications, and AI tools that need structured data rather than pictures. That led to five goals:

  1. One source of truth. Every colour, font, radius, space, shadow and timing is defined once, as a token, and everything else refers to it.
  2. Grounded in the real product. Nothing invented. Components are lifted from pages that already ship and that the team already agreed on.
  3. Readable by machines as well as people. The catalogue is structured JSON with usage guidance, not only a visual gallery.
  4. Documentation that cannot drift. The docs site is generated from the source, never written separately.
  5. Complete enough to design on. States, mobile layouts, charts, icons and fonts included — so a designer never has to step outside the system to finish a screen.

2.1 The eight brand principles

Tokens capture values; they cannot capture judgement. So I wrote down the rules CSS cannot encode in brand-principles.md. It deliberately never repeats a token value — it points to them — and it is written to be read by people and by design agents alike.

PrincipleThe ruleWhy it matters for Curie
1. Dark canvas, alwaysEvery page sits on --color-bg-primary; panels float dark-on-dark. No white cards, no light sections.Sets Curie apart from clinical white interfaces; easier on the eyes between patients and on night shifts.
2. Two fonts, no moreManrope for everything; Playfair Display only for a hero headline, pull quote or single display number.Manrope stays readable small on phones; a touch of Playfair adds editorial authority.
3. Colour only from tokensNever a raw hex. The --text-* opacity ladder is the hierarchy device. Purple leads; teal, cyan, blue, green, pink are sparing accents.Keeps pages calm and the brand recognisable.
4. RestraintOne accent gesture per view.Over-decoration reads as off-brand faster than anything else.
5. Glass via existing componentsFrosted cards come from reusing .card, .editorial-card, .brief-item… not re-deriving the recipe.Depth on a dark canvas, consistent everywhere.
6. Hover on every interactiveEvery clickable has a hover state timed by --duration-*.Makes interactivity obvious on dense content pages.
7. Reuse over inventionA new layout is an arrangement of existing components plus layout-only CSS.Keeps the brand consistent as a small team ships fast.
8. Chrome is cloned, never redesignedSidebar, top bar and footer come verbatim from a golden page.Every page feels like the same product.

3. My process

The process ran in seven stages. The first five produced the system; the last two are where it met the team and changed because of them. The whole build — 55 commits — took sixteen days, from 8 to 23 July 2026.

Stage 1 — Audit what already exists

I started from the product, not from a blank canvas. I went through the Figma files and the live Curie pages side by side, listing every recurring colour, type size, radius, spacing value and component, and noting where Figma and the built pages disagreed. Where they disagreed I reconciled them — the very first commit records fixes to a related-story aspect ratio, the podcasts header padding, the sidebar radius, a game-card icon, per-page header icon sizes and the sign-up card.

Stage 2 — Make the golden pages the ground truth

I chose eight real Curie pages as the golden pages: Home, Briefs, Brief detail, Editorial, Editorial detail, Games, Podcasts and Newsletter. These became the reference everything else answers to. This was the most important decision in the project:

  • Component CSS is reconciled to the golden pages, not the other way round.
  • Every component's documented markup is lifted verbatim from a golden page — never invented.
  • Every later change is checked against a hard rule: the eight desktop pages must render byte-for-byte identically afterwards. This invariant is repeated in nearly every commit message, and it is what kept the system honest while it grew from 23 to 68 components.

Stage 3 — Tokenise every value

I extracted every value into CSS custom properties in tokens.css: 114 tokens across 18 groups, from backgrounds and the purple scale to the text-opacity ladder, motion, z-index, breakpoints and mobile chrome sizes. A small script, build-tokens.js, reads the comment headers in that file and generates tokens.json, so the machine-readable version can never be edited out of step with the CSS.

Stage 4 — Catalogue components with usage judgement

For each component I wrote a structured entry in components-manifest.json: not just what it looks like, but when to use it, when not to, its anatomy, how it behaves, which golden page it came from, and a canonical HTML snippet. This is the part that makes the system useful to developers and to AI — it carries the designer's judgement, not only the pixels.

Stage 5 — Generate the documentation

I built the documentation site with Eleventy so that it reads the package and generates every page from it: token swatches from tokens.json, one page and one live preview per component from the manifests, the asset gallery from assets-catalog.json. Previews load the real components.css. A GitHub Actions workflow rebuilds and publishes the site on every push. Change the source, and the documentation follows — it cannot drift.

Stage 6 — Review, feedback and iteration

Once the system was usable, I put it in front of the people who would depend on it, and most of the growth came from what they asked for:

The team imported the system into Claude Design and began designing features on top of it. That is described in section 7, and the results in section 8.

4. The architecture

The system is organised in four layers. Each layer only reads from the one above it, and nothing below the first layer holds its own copy of a value. That single rule is what makes it a source of truth rather than one more copy.

4.1 Layer 1 — The source of truth (`package/`)

Everything a consumer needs lives in one folder, and consumers read only this folder. It holds four kinds of thing:

KindFilesRole
Valuestokens.css → tokens.jsonEvery colour, font, radius, space, blur, shadow, motion, z-index and breakpoint. CSS is canonical; JSON is generated.
Stylingcomponents.css, layout.css, utilities.css, responsive.css, fonts.cssHow components look. responsive.css is the only file allowed to contain @media rules.
Knowledgecomponents-manifest.json, components-mobile-manifest.json, charts-manifest.json, assets-catalog.json, brand-principles.mdWhat exists, when to use it, how it is built, and the rules behind it — structured for people and machines.
Referencesexamples/ (8 golden pages), assets/ (logos, icons, illustrations, fonts)The ground truth every component is lifted from, and the brand's visual assets.

4.2 Layer 2 — The build

Eleventy turns the package into a website without duplicating any of it. Small data loaders in docs/_data/ read the JSON files; Nunjucks templates paginate over the manifests so each component gets its own page and its own preview automatically; and a preview harness renders each specimen in an iframe that loads the real stylesheets. GitHub Actions runs the token build and the site build on every push to main and publishes to GitHub Pages. Each build writes roughly 280 pages.

4.3 Layer 3 — Published surfaces

  • The documentation site, for people — foundations, desktop and responsive layouts, desktop and mobile components, charts and the asset gallery.
  • JSON endpoints, for machines — /api/tokens.json, /api/components-manifest.json and /api/assets-catalog.json, republished by every build so tools can fetch the current system over HTTP.
  • The package itself — the CSS, assets and golden pages, which a tool or project can pin to a git tag.

4.4 Layer 4 — Consumers

Designers browse specimens and copy golden layouts; the whole system is imported into Claude Design, where the team builds mockups on top of it; AI agents and plugins read the manifests and brand principles directly and are told to carry no copies; and developers receive manifest specifications with purpose, anatomy, snippet and states. Everyone reads from the same source.

4.5 Key architectural decisions

DecisionWhy I made it
Golden pages as ground truthGrounds the system in what already ships and what the team already agreed on. Prevents invented components and gives a concrete test for every change (byte-identical desktop).
CSS is canonical; JSON is generatedDesigners and developers edit one familiar file; the machine-readable copy is regenerated, so the two cannot disagree.
Manifest entries carry judgementwhenToUse, whenNotToUse, anatomy and interactions let a developer or an AI tool choose the right component, not just render one.
Snippets are verbatim, never inventedWhat the docs show is exactly what ships, so a mockup built from the docs matches the product.
One file, two layoutsEach golden page carries its desktop layout and a purpose-built mobile view (.m-view). Copy one file and you get both breakpoints.
responsive.css is the only @media fileUses only max-width queries, so mobile rules activate below a breakpoint and can never change a desktop pixel.
Docs generated from the packageDocumentation that is derived cannot go out of date.
Machine-readable endpointsAI tools get structured data over HTTP instead of screenshots, which is what lets Claude Design design with the real system.
No chart libraryCharts are pure HTML, CSS and inline SVG mapped to brand tokens, so they work anywhere a static page works — including in Claude Design mockups.
Self-hosted fontsManrope and Playfair are vendored as woff2 so pages render correctly offline and in standalone exports.

5.3 Golden page templates and responsive design

The eight golden pages double as the reusable page templates. They map onto four archetypes a designer can start from — Home (index), List (briefs), Detail (brief detail) and Form (newsletter) — with Editorial, Editorial detail, Games and Podcasts as further references.

Seven of the eight pages are responsive. The model is simple and strict: each page ships its untouched desktop content and a hand-built mobile view in the same file. At 600px and below, the desktop content is hidden and the mobile layer is shown, with its own chrome — a top app bar, a bottom tab bar, a drawer, a bottom sheet and floating action buttons. Because all of this lives in responsive.css behind max-width queries, the desktop render stays byte-for-byte identical. The merged mobile pages were verified pixel-identical to the source mobile designs at 390px.

5.4 Assets, charts and fonts

  • 100 catalogued assets — 78 icons (navigation, content-type, game, form and 16 general UI glyphs) and 22 illustrations (podcasts, games, onboarding, marketing, empty and success states). Each catalogue entry has a description, tags, the pages it is used on, its context and dimensions.
  • 7 on-brand charts — bar, stacked bar, donut, radial gauge, radial progress, line and sparkline. They follow familiar chart patterns but are rebuilt in pure HTML and inline SVG, with the series palette mapped to brand tokens and Curie-specific example data (briefs read, weekly reading goal, CME credits).
  • Self-hosted fonts — Manrope (400–800) and Playfair Display (500–600, italic) in latin and latin-ext, so exported pages render correctly anywhere.

6.3 The editing workflow

  • Change a token → edit tokens.css, run npm run build.
  • Add or edit a component → edit components.css, add or update its manifest entry with a snippet copied from a golden page. The docs page, nav link and preview are generated automatically.
  • Change mobile behaviour → edit responsive.css only.
  • Add an icon or illustration → drop the file into assets/ and add a catalogue entry; it appears in the gallery.
  • Release → bump the version and tag; the site header shows which version it was built from.

6.4 The documentation site

The site's navigation follows how people look for things: Overview, Foundations, Desktop layouts, Responsive layouts, Desktop components, Mobile components, Charts and Assets, with direct links to the JSON endpoints. Component groups collapse and remember their state. Every component page shows its purpose, a live preview, its variants and states, and its snippet. I built the site in Curie's own visual language, so the documentation is itself a demonstration of the system.

7. How the team uses it today: Claude Design

The clearest sign that the system works is how the team uses it day to day. Everyone on the team has the Curie Design System imported into Claude Design. When a new feature needs designing, they start a mockup in Claude Design on top of the system, rather than from a blank canvas or from a generic AI layout.

7.1 Why this works

Claude Design can only be as on-brand as what it is given. The architecture was built for exactly this kind of reader:

  • Tokens give it Curie's exact colours, fonts, radii, spacing and motion — so it never guesses a purple.
  • Component manifests give it a catalogue of real components with usage guidance and verbatim markup — so it composes from Curie's cards, buttons and headers instead of inventing new ones.
  • Golden pages give it complete, proven page layouts on desktop and mobile to start from.
  • Brand principles give it the judgement: dark canvas, two fonts, one accent per view, reuse over invention, chrome cloned not redesigned.
  • Assets, charts and fonts mean the mockup can be finished entirely inside the system.

7.2 The workflow

Before the systemWith the system in Claude Design
Rebuild cards, headers and buttons for each new screenStart from the imported system; compose existing components
AI tools produce a generic interpretation of "dark and purple"Mockups match Curie's design aesthetic and design language from the first draft
Re-decide states and mobile behaviour each timeStates and mobile layouts are already defined
Developers receive screens and guess the detailsMockups are built from components that already have a specification

This is what lets the team keep pace with a weekly release rhythm: the design work starts at the level of composing a feature rather than re-drawing the brand.

8.2 Measuring it from here

The team does not yet track formal metrics, and the honest position is that the evidence so far is adoption and qualitative feedback. Useful measures to add next would be: time from brief to approved mockup; number of design-review comments about off-brand details; share of new screens built entirely from existing components; and release frequency per surface. A sibling tool, the Curie drift scanner, already measures how closely the live site's colours, type, spacing and radii match the system's tokens, and could track that trend month by month.

9. What I learned

LessonHow it showed up
Ground the system in what already shipsLifting components from golden pages, and testing every change against byte-identical desktop renders, meant the system never drifted from the product — and the team trusted it.
Design for three readersWriting usage judgement into structured JSON is what made the system useful to developers and to Claude Design, not just to designers.
Generate, don't duplicateBecause every docs page is generated from the package, adding a component never meant writing documentation separately — the page, nav link and preview appeared on their own.
Let the users shape the scopeMost of the growth (36 → 68 components, mobile, states, charts, icons) came from a developer review and a team gap list, not from my initial plan.
Cut what duplicatesThe Templates section and the standalone Subscribe page were removed as soon as they proved redundant.
A source of truth must live where things are builtA system in its own repository is still one step away from the product code. That realisation drives the next phase.

10. What comes next

Today the flow is: design system → Claude Design → a developer re-implements the mockup in the product code. Each step is a place where the shipped product can drift from the brand — the three different purples found in the codebase are proof. On 28 July 2026 I prepared a hand-off package to bring the system into the product codebase in three phases:

PhaseWhat it doesStatus
1. TokensDrop-in SCSS: canonical Curie tokens plus a bridge that maps the app's existing token names onto them, so the app picks up the correct brand values with no component changes. Includes a value-by-value reconciliation table.Ready to apply; two colour decisions and one radius-scale collision flagged for review
2. ComponentsExtract shared primitives (Button, Modal, Toast, form controls, Badge, App Shell, Page Header) as React components that consume the tokens. Scoped by an inventory mapping all 68 components to the codebase.Scoped
3. Design skillA curie-ui skill in the repository that teaches any builder — a developer or an AI agent — to produce on-brand Curie UI by construction: the brand principles, token rules, a worked page and a self-check.Drafted

The goal is the same as the one this project started with, carried one step further: tokens, components and design rules all living where the product is built, so what is designed and what ships are the same thing.
